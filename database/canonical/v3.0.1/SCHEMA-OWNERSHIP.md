# CAN OS v3.0.1 | Canonical entity ownership and lifecycle

**Status:** Database integration candidate, not a production sign-off. **Scope:** `education_v30` and `education_v30_secure`; independent organizations and sites do not require networks.

A Blueprint is a reusable recipe. An Offering is a publisher-owned, versioned educational product. A Deployment is the adoption of an Offering by one Operation. An Operation's `kind_code` is descriptive and never itself authorizes services.

| Domain / service | Canonical read entities | Canonical write entities | Lifecycle boundary and rule |
|---|---|---|---|
| Identity and operations | `organizations`, `sites`, `education_operations`, their role/participation tables | organizations, sites, operation/site roles | Organization, Operation, Site, Network are separate identities. Networks optional. Operational authority requires scoped effective role decisions. |
| Blueprint Studio | `blueprints`, `blueprint_versions`, `blueprint_components`, `blueprint_configurations`, configuration versions/components | configuration versions/components; component approval decisions; `configuration_reviews` | Draft recipe/configuration → approved version → frozen configuration. Never mutate a published/frozen definition. |
| Blueprint references | `blueprint_reference_items`, versioned reference items, religious-affiliation options | reference selections within Blueprint configuration components | Curated items are planning references, not executable Programs or Offerings. Program-model references remain distinct from proposed local clubs, activities, community work and experiences. |
| Blueprint Execution | `configuration_reviews`, component approvals, `blueprint_execution_batches` | batches, `blueprint_outputs` | One idempotency key per executing organization; executed batch only; output can reference Operation, versioned Offering, or existing-Offering Deployment. Multiple distinct Deployment outputs per execution allowed. |
| Product catalog | `offerings`, `offering_versions`, `offering_courses`, families | publisher creates versioned content | One Offering can be reused by many Operations. Selecting a published CAN Offering creates a Deployment/adoption, never a copy of the Offering. |
| Deployment and activation | `program_deployments`, `deployment_sites`, `deployment_offering_adoptions`, `deployment_operating_contexts` | deployment/configuration, adoption, operating context | `planning → review → authorized → active → suspended/closed`. These status labels are not permission; a current stage authorization is still required. |
| Qualification | `qualification_definitions`, versions, questionnaire bindings, evidence, applications, reviewer authorizations | site qualification applications, evidence submissions, reviews, decisions | Publish immutable policies; maintain append-only verified decisions; reuse the same evidence version across applicable requirements, with its original ownership/scope. |
| Program fit | `qualification_program_fit_*`, `qualification_program_availability_rules`, `evaluation_bases` | fit assessments, requirement findings, reviews, bases, invalidations | Catalog availability can be inspected before an application; detailed fit and stage activation require current evidence, review, and authorization. |
| Facility, staff and equipment | `site_spaces`, capability assertions/verifications, qualified personnel, shared resource pools | verifications, resource allocations, improvement actions | Resources are verified and time-bound. Site capability does not automatically permit an Offering. Safeguarding/readiness requirements differ by program. |
| Learner instruction | `learner_course_attempts`, progress, `instructional_track_policy_versions`, `learner_track_selections`, official assessments | learner attempt/progress, immutable track-selection revisions, independently governed official outcomes | `learner_course_attempts` is authoritative for participation. Track selection requires a current published policy and distribution authorization; switching never resets grades or assessments. Section optional for standalone learning within a Deployment. |
| Practice submissions | policy-scoped `formative_practice_attempts` | immutable practice history; raw answer JSON in `education_v30_secure.formative_practice_responses` | Practice requires a current eligible policy/track when presenter-specific. Answers are restricted and separately retained; changing teacher does not erase prior attempts. |
| Noncredit training | `noncredit_training_versions`, registrations, participation/completion | registration, attendance, evidence-backed completion | Noncredit registration is separate from school enrollment. Continuous analytics use `learner_longitudinal_outcomes` rather than inventing a second enrollment system. |
| Content governance | `content_publication_manifests`, manifest items, reviews, track-policy withdrawals and content withdrawals | immutable approved manifests, independent decisions, append-only withdrawals | A track cannot publish without an approved manifest and independent track reviews. An approved Offering does not make every track or asset deliverable; recheck current rights and withdrawals at delivery. |
| Instructional authoring and delivery commands | `instructional_tracks`, `instructional_track_versions`, track materials/presentations/reviews, shared publication manifests, course-scoped professional assignments, command receipts | versioned draft authoring, immutable submitted snapshots, independent review/publication decisions, learner choices and practice history | Provider commands require an active verified organization grant and evidence-backed course-scoped assignment. Learner services recheck enrollment/registration and guardian relationships. Track manifest items bind each asset hash to current verified rights evidence. Wrappers are not route-wired; deny-by-default RLS, protected media delivery, and authorization/database acceptance tests remain required before exposure. |
| Public school/center experience | `operation_publication_snapshots`, `program_publication_claims`, `publication_withdrawals` | reviewed snapshots and stage-specific claims | Publication is a time-bound public projection. `v301_current_public_program_claims` hides superseded/revoked/withdrawn claims. Proposed is distinct from approved/enrolling/operating. |
| Safety and feedback | surveys, `assurance_cases`, secure safeguarding reports, improvement plans | feedback, cases, actions, verification | Sensitive safeguarding contents stay in secure schema. Network membership grants no private student or safeguarding read rights. |
| Funding, outcomes and impact | sources, allocations, `initiative_metric_definition_versions`, snapshots and observation sources | approved evidence-backed metrics, verified funding flows | Annual/impact reporting is reproducible; never equate registration, attendance, and demonstrated outcome. |

## Application service ownership

- **Launch Studio** owns user-driven proposed Operation, Site, Blueprint configuration, and plan actions. It never writes operational authorization decisions as a side effect of a checklist.
- A Blueprint configuration's self-declared organizational identity is independent of the host Organization's identity or role; affiliation choices do not establish network membership.
- **Catalog service** reads published policy versions and public program availability via `v30_catalog_program_availability`. Geography, modality, and provider support are distinct from legal approval.
- **Qualification service** owns the assessment request, answer/evidence collection, and reviewer workflow. It reuses evidence by stable version identifiers.
- **Policy/activation service** exposes `v301_policy_evaluation` and stage-specific preflight. It must re-evaluate from the database when a stage is invoked; it cannot trust a cached UI status.
- **Academic delivery** uses `learner_course_attempts` and stable course-level assessments; a recorded-presenter switch updates only the track selection history.
- **Publication service** writes authorized claims; the public read model is `v301_current_public_program_claims`. Public pages must not project raw Blueprint/Launch Studio proposals as approved programs.
- **Reports** use consent-scoped aggregate read models; they cannot infer network-wide permission from network participation alone.

## Change-safety rules

Published version identity and exact evidence versions are stable. An existing published artifact gets a new version, a withdrawal event or a superseding decision, not an in-place rewrite. For teacher switching, update/supersede the current selection and insert a new selection **within one transaction under a locked `learner_course_attempts` row**; the partial unique active-track index rejects conflicting writers. For Blueprint execution, reuse the original batch keyed by `(executing_organization_id, idempotency_key)` in the same transaction; do not blindly insert another output.
