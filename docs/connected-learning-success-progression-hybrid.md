## Parallel safeguarding pathway — high priority before onsite launch

Onsite room facilitators/site leaders are first observers of possible abuse/neglect, exploitation, serious bullying or violence, substance-related danger, threats and other welfare issues. These **cannot** be treated as routine academic intervention tickets. Implement [Site Safeguarding and Welfare](./site-student-safeguarding-and-welfare.md) as a distinct restricted incident workflow with urgent response, jurisdiction-specific outside reporting duties and separate school/site accountability. Authorized downstream support tasks may link to it without exposing confidential allegations. This is a **site-opening safety gate**, not optional P3 analytics and not fulfilled by the existing `incident-service` tables.

## 2. Teacher intervention

**Existing canonical owners:** `teacher-today.functions.ts`, `teacher-missing-work.functions.ts`, `support-referrals.functions.ts`, `academic-intervention` actions, `insights`, `notifications`, and audit/event infrastructure. Do not create a competing referrals table or intervention engine.

**Mandatory multidisciplinary integration:** Counselors, academic coaches, tutors, specialist service providers and paraeducators must participate in the **same student support case** using explicit case/service assignments, distinct privileges and disclosure-safe summaries. A teacher's academic Action may hand off to an assigned case coordinator without converting private counseling material into a teacher-readable Action. See [Multidisciplinary Student Support Cases](./multidisciplinary-student-support-cases.md) for roles, referral/service handoffs, confidentiality boundaries and negative-access acceptance. Current `specialist`/`counselor` site-wide access is not a sufficient final authorization model, and a scoped paraeducator/service-provider role is not yet implemented.

**New P1 gate:** Implement named case coordinator + participant/service assignments and server-enforced case-level visibility **before** treating teacher-to-counselor/paraeducator integration as complete. Existing referral plans/services are a foundation, not proof of full integration.

**First new slice:** `getTeacherLearningEvidence` and Teacher Today display observed last-7-day interaction evidence only within live assigned Sections and enrolled students. It is descriptive, never an auto-generated risk diagnosis.

**First teacher-action bite committed:** Teacher Today now offers `TeacherLearningFollowUpForm` for a student with verified, recent recorded interactions. A teacher must enter an independent observation, choose check-in/work review/tutoring, and choose a 1/3/7-day deadline. `createTeacherLearningFollowUp` rechecks the assigned active section, current enrollment, student/section/version-matched event and organization/site/program scope in the transaction; the teacher becomes the Action owner. It stores the specific event as descriptive evidence, deduplicates open Actions for that event, emits the standard `ActionCreated` event and audit record, and does **not** automatically flag students as at risk or notify guardians. No new referral table or workflow was introduced.

**Follow-through code bite committed:** `getTeacherLearningFollowUps` now presents active and recently resolved, current-teacher-owned academic Actions only for active enrollments in currently assigned Sections. Teacher Today displays due dates and selected support approaches. `resolveTeacherLearningFollowUp` requires the current owner to record what support was delivered, a teacher-assessed outcome and the evidence/next step; it verifies section, enrollment, ownership and current role/grant scope again inside a transaction, then reuses the canonical `resolveActionInTransaction` ActionResolved event and audit. Repeated closes are idempotent. Student activity signals remain descriptive; no automatic mastery or attendance claims, no guardian/counseling disclosure, and no new schema.

**Next build:** Verify the follow-through write on isolated Neon and in browser sessions, then measure changed outcomes using subsequent *academic work* (grading, retries, teacher assessment, submitted work), not telemetry alone. Keep private support/counseling notes restricted and integrate student-appropriate notifications only after testing visibility and consent rules.

**Acceptance:** teacher sees verified evidence and missing work; initiates human-reviewed follow-up; student receives appropriate notification; ownership, response, and outcome persist; another teacher cannot see or act on untaught Sections.

## 3. Student success

**First new slice:** `deriveClassNextSteps` produces a nonauthoritative next published lesson, self-reported completion counts, submissions awaiting teacher feedback, and revision suggestions. Class Workspace now shows it for student/related guardian. It never claims mastery or earned credit.

**Cross-class Student Today bite committed:** `deriveStudentSuccessPriorities` now prioritizes assignments from the existing enrollment-scoped `getAssignments` service across every currently enrolled class. It includes published assessments **before any submission exists**, overdue unsubmitted work, returned revisions, due-soon tasks, saved submissions awaiting feedback, and graded feedback review; it does not treat a late **submitted** assignment as still missing. `StudentSuccessPriorityPanel` provides exact assignment deep links, a bounded prioritized queue, and an unavailable-data state rather than pretending no work exists. Student Today summary counts now use canonical assignments instead of counting only submission rows when available. The existing lesson-specific `deriveClassNextSteps` remains in Class Workspace.

**Next Student Success support bite committed:** Student Today now also reads the authenticated student's existing, student-owned Actions through the canonical `getQuickWinActions` service, projects **only** supported `student_recovery`, `student_support`, `student_support_request`, and `conference_follow_up` types, and presents a bounded due-date support queue with exact assignment/Action links. No private staff metadata, observations, counseling referrals, safeguarding case records or `academic_intervention` Actions enter this projection. Failed Action reads appear as **unavailable**, never as an empty queue. Student-owned Actions already shown in the previous generic Today area are de-duplicated from the new panel. No schema changes, no new support case or referral engine.

**Teacher-approved academic goal handoff now committed:** `shareTeacherStudentGoal` permits the currently assigned teacher to publish **one explicitly authored student-owned `student_learning_goal` Action per active teacher-owned academic follow-up**. It verifies the source Action's owner, section, active enrollment, role and scope, and serializes duplicate requests using a source row lock. Its new title/instructions are teacher-entered and require explicit confirmation that the text is suitable for student disclosure. It **never copies** the private Action's observation, evidence, history or metadata. The child Action is linked to its parent by `parentActionId`, remains separately owned by the student, and is visible in the existing Student Success support queue. The student **cannot self-resolve** this special goal; teacher review remains necessary. No new table or case workflow is introduced. Unit and disposable-DB integration assertions are committed, but CI is blocked before runner assignment and connected browser acceptance is not yet proved.

**Teacher-reviewed goal follow-through committed:** `getStudentGoalGradedEvidence` lists eligible latest-attempt graded submissions from the SAME enrolled student and Section, graded after the explicitly shared goal was created. `reviewStudentLearningGoal` rechecks the teacher's ownership of the private originating Action, live staff/Section/enrollment scope and actual submitted academic evidence, then records a teacher-chosen result (met / needs more practice) and independently student-safe feedback. Met resolves the student goal; more-practice keeps it in progress for subsequent new graded evidence. The graded assessment itself, course credit and private staff Action remain unchanged. Event + audit entries are written for the decision. Teacher Today contains the graded-evidence selector/review form; Student Today reads the safe review feedback and recent confirmed goal completions only. Students cannot self-complete or self-review these goals. Unit/policy tests and a rollback-isolated same-school graded-submission acceptance extension are committed but **GitHub CI is failing before runner assignment and none of these newest checks are verified as passing**; authenticated browser acceptance remains pending.

**Next build:** Use those teacher reviews for cross-class student goals and pacing plans, then safe relationship-scoped family summaries and progress against program-specific academic targets. Do **not** auto-disclose counseling or safeguarding records or infer mastery from activity clicks. Do not expose private counselor cases, safeguarding notes, privileged accommodations, or staff-only Actions. Guardian summaries require their own scoped read model and relationship/revocation tests. **Connected/role-session browser acceptance for this new view remains outstanding.**

**Acceptance:** same authenticated student across courses; tasks and deadlines agree with canonical submissions and schedule; refresh does not lose state; related guardian sees authorized subset; revoked guardian and wrong-school users are denied.

## 4. Academic progression

**First new slice:** `assessAcademicProgression` computes provisional subject-category credit gaps from supplied reviewed course evidence and an explicit requirements matrix. Unknown, unfinalized and unapproved transfer credit cannot be counted. It always returns `diplomaAuthorized: false`.

**Recorded-credit inventory now committed:** `summarizeRecordedTranscriptCredits` consumes the EXISTING guardian/student transcript projection, grouping actual finalized terminal-period course credits by **issuing institution and recorded course subject**. The report-card transcript view now shows earned/attempted units, missing data, failed/withdrawn courses and conflicts without double-counting quarterly/interim periods. It never adds credits from another issuing institution as if a transfer were approved. The transcript query now includes course subject and terminal-period provenance; older rows without sufficient provenance explicitly display "unable to summarize" instead of inventing credit. Transcript issuance itself is unaffected by incomplete credits. Unit, SSR and isolated-database assertions are committed, but runner/connected CI and real browser acceptance remain **unverified**. There is still **no authoritative graduation requirements configuration, transfer approval review, diploma eligibility or issuance**.

**Next small bite:** versioned institution/cohort graduation requirements with qualified-registrar review, then a scoped category-gap reader projecting ONLY recorded eligible credits against that approved version. Keep transcript issuance independent of graduation rules.

**Next build:** Institution- and cohort/version-specific graduation requirements; required courses/subject units, substitution/waiver policy, official awarded and transfer credit evidence, school-year/term progression, human approval, missing-credit explanations and a graduation-readiness workspace. Integrate `section_grades`, `transcript_issuances` and real authorized credit issuer; do not silently assign missing credit.

**Acceptance:** a transcript may be issued showing unknown units; graduation review blocks incomplete criteria; qualified school official explicitly approves; diploma issuance is a different audited state transition with immutable snapshot and reissuance/correction policy. The current helper is not proof of graduation readiness.

## 5. Hybrid-site operations

**Existing owners:** `site-today.functions.ts`, `onsite-attendance-workflow.functions.ts`, expected attendance, calendar/scheduled occurrences, site/program scopes, Actions, handoffs and Site workspace. Reuse these; do not treat online learning engagement as daily attendance.

**First new slice:** `summarizeHybridSiteDay` distinguishes expected onsite students, staff-recorded present/tardy/absent events, unresolved attendance, and separately observed online activity. No client event can mark a child present.

**Onsite day attendance slice committed:** `room_facilitator`, `site_staff` and `site_leader` now receive only `onsite.attendance.record` beyond their pre-existing safeguarding-report stub, **not** broad `attendance.write`, enrollment, grades, guardian excuse review, counselor or incident-case access. Verified original site-bound grants are rechecked in the handler, the canonical attendance service and the locked attendance transaction. The existing scheduled onsite roster is reused; original enrollment/program/site and academic calendar/schedule constraints remain mandatory. An authorized staff member can mark present/tardy/absent for an expected student, review prior official marks, and make a recent (30-day) reasoned correction subject to optimistic record-ID conflict checks. The original append-only attendance events, guardian absence notices, audit trail and idempotent mutation keys remain canonical. The new `/site/day` workspace shows a school-timezone day, expected roster entries, marked/unrecorded counts and a correction-reason field. It **does not** provide checkout, custody authority, guardian excuse details, student gradebook or localStorage copies of student rosters. Paraeducators are NOT authorized to mark attendance by default.

**Instructional coverage slice committed:** `getOnsiteSupervisionPlan` reads this same original site-bound staff role, current onsite programs, active school-year/term sections, assigned instructional schedule template periods and active delivery arrangements. An adult assignment is treated as a PLANNED shift only when their identity is active and a non-synthetic, active account/staff grant belongs to the same site; a missing grant, absent facilitator, unscheduled section, conflicting assignment or double-booking is flagged. `OnsiteSupervisionPanel` is a separate read-only area of `/site/day`: it lists planned instructional blocks and assignment gaps, explicitly labels physical room assignments as **not represented in the current model**, and warns if records are capped or unavailable. No individual student record, counseling/safeguarding case, physical presence, onsite duty acknowledgement, authorized release or checkout is introduced. The existing `delivery_arrangements`, `schedule_template_periods`, verified staff grants and active sections remain the source of truth. Unit policy tests and rollback-isolated site-role/staffing read assertions are committed, but **GitHub Actions is failing without runner-executed steps; these new tests, server typechecking, and browser acceptance are NOT verified passing.**

**Daily attendance reconciliation slice committed:** `deriveOnsiteDayReconciliation` compares the existing expected onsite roster against current authoritative event IDs/status, per program and across distinct students. It flags unmarked entries, impossible/stale statuses, duplicate student-program entries and missing calendar configuration. No unmarked student is assumed absent. `OnsiteDayReconciliationPanel` is wired directly into `/site/day`. A VERIFIED site leader whose current site grant covers **all active onsite programs at the site** can explicitly attest to one complete attendance observation snapshot using `attestOnsiteDayReview`. The attestation is an audited, idempotent resolved `actions` record scoped to the original site, storing only counts and a SHA-256 roster/event fingerprint, not students' names or restricted notes. Subsequent changes that affect the expected roster/status/event IDs or summarized calendar configuration make the previous attestation display as stale. This is a snapshot-level *administrative attendance review*, NOT a lock on attendance, legal school closure, a guarantee that adults are onsite, student sign-out, custody authorization or a guardian-excuse adjudication. A room facilitator or site staff member can view the scoped review but **cannot sign off**. No database migration is needed.

**Minimum duty-response bite committed:** Current-site, named facilitators can now acknowledge their availability for an authorized instructional block or report they cannot cover it. `getOnsiteSupervisionPlan` computes a self-only response permission and SHA-256 plan fingerprint from the actual assigned adult, class, block schedule, site, date and staffing/grant state. `respondToOnsiteDuty` revalidates the plan at write time, requires today's school-local date, disallows answering another adult's assignment, rejects conflicted acceptance, and stores a single immutable `onsite_instruction_duty_response` Action per fingerprint, with a transactional advisory lock and audit record. Exact retries are idempotent; contradictory responses cannot quietly overwrite a coverage exception. `getOnsiteDutyResponses` limits results to current, verified blocks and records missing acknowledgments and declared staffing gaps. Site leaders can view gaps but cannot impersonate a facilitator. This reuses canonical Actions and schedule/assignment grants; no new table or room/facilities subsystem. **Duty responses are only staff-declared availability:** there is no proof of physical arrival, continuous supervision, accepted handoff, notification delivery, or emergency coverage. The UI instructs staff to contact the site leader directly when unable to cover a block. Safety/safeguarding remains a separate non-operational stub.

**Verification-focused correction committed:** The repeating weekday instructional schedule is **not** sufficient to accept a duty. `getOnsiteSupervisionPlan` now joins the latest active institutional calendar version to the exact selected day and denies staff coverage/duty responses for closures, holidays, zero-instruction days and missing instructional evidence. `getOnsiteDutyResponses` marks outdated responses inactive when a calendar/assignment change invalidates the duty fingerprint, and excludes closed or unplanned blocks from outstanding duty counts. The existing rollback-isolated attendance integration test checks the full path: original scheduled duty → acknowledged → school-calendar closure → acknowledgment invalid/response denied → instruction restored. New unit tests cover calendar gaps. The tests are committed but cannot be certified as passing while CI jobs fail before any runner steps execute.

**Remaining next:** Connected server/typecheck and browser acceptance for the combined onsite roster, supervision, duty and reconciliation workflow. Then only if needed introduce a narrow verified incoming-person handoff and room assignment with approval, rather than a general facilities management system. Child checkout and safeguarding reporting require distinct policy/legal gates. The repository's GitHub Actions currently fails without starting the runner, so new tests are committed **but not verified passing**.

**Acceptance:** a local facilitator can operate one authorized site/day without accessing sibling sites; arrivals, departures, exceptions, room supervision and parent notifications are verified by real staff roles and evidence. Separate online student work remains visible only to authorized educators and never automatically changes official attendance.

## Engineering/quality gates

- Code owner for each capability owns the server boundary. Verify capability + resource + scope + relationship for every query/command.
- CI must cover build, typecheck, unit and migration-generation parity on a single commit.
- Add disposable-Neon integration and multi-role browser acceptance for each write path. Unit-only or schema-only results remain unverified.
- Keep append-only and idempotent evidence for substantive state changes, avoid recording high-frequency telemetry as security audit events.
- Limit/minimize child telemetry: strong opt-in/notice, data minimization, retention/subject access policies and robust aggregation; consult school counsel before claiming COPPA/FERPA compliance.
- Do not add speculative automatic AI risk predictions; require transparent, teacher-reviewable evidence and human control.
