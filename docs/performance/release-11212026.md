# CAN OS performance release: 2026-11-21

Branch: `release-11212026` (created from `main`).

## Goals

Improve perceived navigation speed, reduce server-function calls, and establish production measurements without weakening authorization, data completeness, auditability, or tenant isolation. Synthetic demo Sites must follow the same execution path as other Sites.

## First improvement

- Launch Studio formerly read Site Information, Program & Audiences, and Marketing Packages once for overview completion and then read the same data again for the active module.
- The loader now reuses successful authorized overview responses, with the existing retry path preserved when an overview read fails.
- Marketing suggestions begin concurrently with overview reads.
- No application approval, publish, or enrollment gates have been relaxed.

## Baseline instrumentation to implement

Record, per route and request, latency and error rate for:

1. Auth/session and role/scope evaluation.
2. Request-scoped Neon pool setup and teardown, connection acquisition, and SQL timings.
3. Route loader and dependent server functions, including count of reads per navigation.
4. Serialized payload size and server response time.
5. Client-side navigation, route chunk transfer, hydration, render, and interaction readiness.

Use coarse, non-PII route labels and correlation IDs. Never log credentials, student records, sensitive query parameters, raw SQL bindings, or cross-tenant data. Sampling and retention must be bounded.

## Next optimization order

1. Profile `/launch/site` and `/launch/website`, then remove remaining duplicate reads and expensive work not needed by the active step.
2. Profile Operations, where `loadOperationsHome` currently waits for actions before beginning four supplementary reads. Separate critical and optional content if safe.
3. Profile Student Class, Teacher Class, and Classroom Connect using persistent data with representative enrollments and lessons.
4. Inspect Neon query plans and index selectivity for the slowest confirmed requests; avoid speculative indexes.
5. Measure Cloudflare Worker cold/warm behavior, connection handling, and JS route chunks.
6. Tune cache freshness only where changes cannot leak access across roles or delay revocation.

## Instrumentation now committed

Set `CAN_PERF_TRACE=1` on the **server** for temporary diagnostics and review `[can-perf]` entries in Worker/server logs. Turn it off after sampling. Records include only hard-coded route/step identifiers, `ok`/`error`, and elapsed milliseconds. Never add a Site ID, user, query text, URL, student identifier or secrets to a timing label.

Current coverage:
- `launch.site`: site options, information, programs, brand, marketing and canonical solution workspace
- `operations.home`: authorized action workspace followed by release health, command center, full-flow dashboard and launches

**Known limitation:** loaders may run in the browser on client-side navigation, in which case this server-only flag does not record that navigation. It is not yet a comprehensive server-function/database trace. The next instrumentation step should be inside the authorized server handlers themselves, or via a trusted request-level boundary, while keeping all records free of personally identifiable data.

## Data-loading improvements and CI follow-up

- Course Registration's active catalog is still scoped to the current actor's Sites/Programs. It now provides those authorized Section IDs to a bulk policy reader that fetches saved policy rows and prerequisites in two queries, regardless of the number of Sections (subject to database parameter limits). A single shared normalizer preserves fallback policy behavior for pre-migration rows. Transactional request/approval policy checks still use the existing one-Section reader.
- Teacher associations are indexed by Section rather than repeatedly filtered for each catalog row. Teacher and policy reads are concurrent.
- Student Home now starts its native Class index independently of the legacy Section resume lookup. The resume lookup processes at most three Section workspaces per batch and resolves results in original priority order, preserving the preferred urgent-work Class and completed fallback behavior. This is a bounded fan-out improvement, **not** yet a lightweight projection: a dedicated summary endpoint remains the desirable long-term architecture.
- Operations supplementary performance timings now wrap the underlying server requests inside `supplementaryRead`, so a failed underlying request is logged as an error rather than appearing successful merely because the wrapper returned a fallback state.
- Regression source-contract coverage: `tests/unit/performance-data-loading-contracts.test.ts`.
- Added `.github/workflows/performance-branch-verification.yml` with a push trigger for `release-11212026`. The workflow checks install, source syntax, local imports, application and Cloudflare builds, TypeScript (postbuild), targeted regression tests and V6.1 lint.
- At the time of this update, GitHub still reported zero runs. A committed workflow is **not** a successful verification run.

### Residual concerns

The bulk reader relies on actor-scoped Section IDs provided by the authorized calling service and should remain server-only. Measure the actual latency and SQL plans of this new path before deciding whether further indexes are needed. Student Home still fetches full Class workspaces to construct a small resume card and should eventually switch to an authorized batch summary reader. Do not broaden per-request caching of student or Site data without explicit identity/grant scoping and revocation handling.
