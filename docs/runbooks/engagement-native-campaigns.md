# Native engagement campaigns (release candidate)
Uses the shared email-channel Engagement and Go Link, not a parallel enrollment flow or marketing-content store. Lists are scoped to the exact owner; sender-level suppression extends across that organization's sites and programs. Consent is operator-attested with a recorded source, not inferred from enrollment. No automatic imports or opt-out overrides. A campaign snapshots its invitation and list membership, with per-recipient receipts and an idempotency key. Both existing 15-minute maintenance schedulers share DB leases. Provider acceptance is not delivery; signed Resend events supply delivery/bounce/complaint evidence.
 
Deployment prerequisites: apply migrations 0115 and 0116 through the reviewed SQL-only chain, configure CAN_CAMPAIGN_FROM_EMAIL (verified Resend sender), CAN_CAMPAIGN_POSTAL_ADDRESS (valid sender mailing address), RESEND_API_KEY, CAN_ACCESS_PUBLIC_ORIGIN, RESEND_WEBHOOK_SECRET and existing restricted Go gateway access. Configure the existing /api/webhooks/resend endpoint for delivered, bounced, complained, failed and suppressed events. No actual recipient sends in development or release validation without explicit test-recipient approval. Test sender identity, SPF/DKIM/DMARC, one-click unsubscribe including automated GET scanners, cross-tenant denial, demo restrictions, concurrent workers, retries, webhook order, opt-out during queue, cancellation, and real receipt reconciliation before enabling live distribution.
 
Initial limit: 1,000 unique addresses per list; up to ten sequential dispatches per maintenance invocation. This is a pilot implementation, not a national-throughput acceptance claim. A production provider quota and throughput/queue SLO review is required for national rollouts. List members can be inspected, removed, and suppressed by an authorized operator. Consent withdrawal records the operator, never silently reactivates a suppressed contact, and applies across the logical sender organization. Ambiguous transport failures are reported as unconfirmed rather than confirmed failures. Contact-retention/deletion policy and re-consent after suppression remain separate governance decisions. Run exact-SHA typecheck, build, unit, database and browser acceptance before deployment. No migration, provider configuration or live send is implied by this commit.

## Reliability follow-up
Both RFC 8058 form encodings are supported through the same bounded request-body reader used by the signed webhook. Verify that actual provider-generated DKIM signatures cover the two one-click headers before launch. Retry timing uses the shared outbound exponential backoff and respects Retry-After; a rate-limit or server-error response stops that dispatch invocation. Ambiguous earlier send outcomes survive a subsequent suppression, cancellation or rejection until authenticated evidence resolves them. Replaying a queued request requires the original schedule; the UI retains the exact request ID and timestamp. No schema change or live send is part of this follow-up.
