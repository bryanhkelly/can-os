# Pilot Blueprint API preparation

### Blueprint-to-deployment preparation (standard APIs)

The `governed` stage now supports `prepare-blueprint` (author, siteId, configurationId, initialVersionId, blueprintId, blueprintVersionId, name, version), `review-blueprint` (reviewer, author, configurationVersionId, reviewId, evidenceVersionId, rationale, components), `execute-blueprint` (executor, siteId, configurationVersionId, reviewId, operationId, idempotencyKey, expectedOfferingVersionIds), and `approve-adoption` (reviewer, deploymentId, offeringVersionId, evidenceVersionId, rationale). Use the same configuration/version identifiers throughout; use the execution receipt's actual deployment identifiers for later stages. The author must have the Site planning grant, the executor needs current Operation/Site authority, and decisions require real independent reviewer authority and evidence. Existing Blueprint review receipts predating the exact component payload cannot be safely replayed; inspect the existing review rather than resubmitting it. New exact receipts permit retries without duplicate decision records.

**Operational boundary:** execution generates planning deployments and proposed adoptions. It does not grant Operation membership, authorize registration or delivery, create deployment placements, record readiness decisions, or activate the deployment. The adoption API requires current independent readiness evidence and Site placements; approval does not itself activate the deployment. The Class preflight explicitly rejects inactive Operations/Deployments and unapproved adoptions. The combined pilot runner is not yet an end-to-end new-organization workflow until these normal operational governance commands are available and verified. Do not use direct SQL business mutations as a substitute. The individual preparation stages are source-level implementations pending live runtime validation.
