## Evidence vocabulary

- **Source present:** Code or executable test exists at the indicated path. This is not verification of correct deployed behavior.
- **Mocked unit:** Business rule or service is tested with controlled data and possibly mocked database/authorization/storage dependencies.
- **Database integration defined:** A test uses a real database when the required test URL/environment is present; many such files use `describe.skip` without `DATABASE_URL`. This status does not mean it passed on the current commit.
- **Connected browser evidence:** Different server-issued human sessions, real commands, isolated schema and the same Site/Program/student across all required steps; must be executed, recorded and tied to the candidate SHA.
- **Independent legal/operational evidence:** Signed/approved procedures, site-specific clearance, responder training, real supervision, mandated external reporting, and professional review. A software test cannot supply this evidence.

## Why the existing suites cannot be conflated

1. `npm test` excludes `tests/integration/**` and `tests/e2e/**`; its passing result does not establish database or browser safety acceptance.
2. `safeguarding-overdue.integration.test.ts`, `onsite-room-plan.integration.test.ts`, and `onsite-day-incident-privacy.integration.test.ts` select `describe.skip` when `DATABASE_URL` is missing. Running these without a disposable database is **not** successful validation.
3. The room-plan integration substitutes the actual adult eligibility reader; the onsite day/incident privacy integration mocks several readers. Their intended narrow focus must remain explicit.
4. The FullFlow browser scenario joins admissions and academics but is **not** a connected legally approved onsite day with all safeguarding/pickup persons. Route smoke merely verifies navigation and does not substitute for workflow execution.
5. Unit tests asserting UI source strings are static guards, not browser proof that the full interaction is usable, accessible or persisted.
6. `src/workers/scheduled-jobs.ts` calls the safeguarding overdue processor. Verify deployed scheduler triggers, permissions, timing, outage response, dead-letter handling and delivery evidence independently; source linkage alone cannot establish a monitored on-call process.

## Repeatable, bounded validation

Run `npm run test:safety` for the focused **unit policy regression subset**, using the safety tests selected in `package.json`; the CI workflow should record its result separately before the typecheck stage. Do not attach a pass status before the relevant GitHub job completes.

Then run the three conditional database integration tests only against a verified **disposable** fully migrated Neon branch, with rollback, correct staff identity, independent verified grants and observable audit/outbox results. Finally execute the all-role school-day browser acceptance described by [Church-Hosted Safety Gates](CHURCH-HOSTED-SAFETY-GATES.md) with a human-approved jurisdiction/operating plan. No production writes or real student data may be used as test fixtures.
